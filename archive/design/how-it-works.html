How the Mumbai Rain app works

Every module, in plain English — what it is, what it does, and how they fit together.

The whole app answers one question: “Will it rain at my Mumbai spot in the next 2 hours?” It does that by taking a free global weather forecast, learning how that forecast is usually wrong for Mumbai, and correcting it. Below is each part of the machine.

The one-line analogy: imagine a weather forecaster who’s often wrong in the same ways. You keep a diary of “what they predicted” vs “what actually happened,” spot their habits (“they always over-warn at 2pm”), and from then on you mentally correct them. This app is that diary + that correction, automated and free.

Module 1 — pipeline/sources.py · the forecast fetcher BUILT

Like: phoning the weather service and writing down what they predict.

Fetches the rain forecast for a Mumbai point from Open-Meteo (free, no signup). It grabs two models: best_match (Open-Meteo’s tuned blend) and ecmwf_ifs025 (Europe’s gold-standard model — our benchmark to beat).

In: a latitude/longitude.   Out: next 24 hours of predicted rain (mm) from each model.

It also has fetch_recent_rain_mm() — how much rain fell in the last 3 hours. That “what’s happening right now” is the single strongest clue for the next 2 hours.

lat / lon sources.py forecast mm

Module 2 — pipeline/labels.py · the truth-checker BUILT

Like: a trustworthy person standing at the airport who tells you whether it’s actually raining.

Pulls METAR reports — real observations from Mumbai airport (VABB), filed every 30 minutes by trained observers, free and no signup. It reads the weather code (RA = rain, BR = mist, etc.) and turns it into a simple yes/no: did it rain this hour?

In: the airport code.   Out: {hour → raining true/false}.

Why this matters most: we check the forecast against a real measurement, not another forecast. If we graded the forecast using another model’s guess, “we’re accurate” would be circular nonsense. METAR is the honest answer key.
METAR code (RA/BR) labels.py rain yes / no

Module 3 — data/log.csv · the diary (the database) BUILT

Like: a notebook with one line per hour: “forecast said X, reality was Y.”

A plain spreadsheet file. Each row = one prediction for one hour, plus what actually happened once it’s known. Columns: when it was forecast, which hour, the two models’ predicted mm, recent rain, and observed_raining (the yes/no truth).

There’s no fancy database — the file lives in Git, which versions and stores it for free. Simple, free, and every row is the model’s study material.

forecast + outcome append row log.csv (in Git)

Module 4 — pipeline/log_snapshot.py · the diary-keeper (logger) BUILT

Like: the hand that writes in the diary every hour — adds today’s forecast, then fills in yesterday’s outcomes.

Ties Modules 1–3 together. Every time it runs it: (a) appends a fresh forecast snapshot (outcome still blank), and (b) backfills the raining answer for past hours using METAR.

Run it: uv run python -m pipeline.log_snapshot.   First live run: 24 rows, 21 already answered.

sources + labels log_snapshot.py new + backfilled rows

Module 5 — pipeline/train.py · the student (the model) NEXT

Like: reading the whole diary and learning the forecaster’s habits — “when they say 0mm at 4am but it rained, expect rain.”

Reads log.csv and trains a tiny model (a calibrated classifier) that takes the forecast + recent rain + hour-of-day and outputs a corrected probability of rain. The goal: cut the forecast’s false alarms (today ~50% of rain predictions are wrong).

Crucially it has an eval gate: a new model is only kept if it beats the old one and the raw forecast on a fair test. So it can only ever get better, never worse.

In: the diary.   Out: model.json — a handful of numbers.

log.csv (the diary) train.py + eval gate rain probability

Module 6 — web/model.json · the cheat-sheet NEXT

Like: the forecaster’s habits written on a sticky note — a few numbers, not a brain.

The trained model exported as tiny weights (a few KB of JSON). The webpage applies it with plain arithmetic (corrected = w₁·forecast + w₂·recent_rain + …) — no AI engine running anywhere, no server, no cost.

trained weights export model.json (few KB)

Module 7 — web/ · the face (the webpage) BUILT (draft)

Like: the friendly front desk that just tells you the answer.

A static page that, in your browser, calls Open-Meteo live, applies model.json, and shows the 2-second verdict (“Dry for 2 hours” / “Rain in ~40 min”). Files: index.html, app.js, nowcast.js (the verdict math), flood.js (Mumbai flood-spot risk). Design spec: docs/frontend-design-doc.html.

Hosted free on Cloudflare Pages. $0 because the browser does the work and the data API is free.

live forecast + model.json nowcast.js 2-second verdict

Module 8 — GitHub Actions cron · the heartbeat NEXT

Like: an alarm clock that wakes the diary-keeper every hour, forever, for free.

A scheduled job on GitHub that runs log_snapshot.py every hour and commits the new rows to log.csv, then retrains daily. This is what makes it “self-improving” — it runs 24/7 with your computer off, at $0. Without it, the diary only fills when you run it by hand.

clock: every hour GitHub Actions commit new rows

Each beat: a new diary row, the cycle turns, the model gets a little sharper. (Animated; static frame shown with motion off.)

How a single rain verdict happens (end to end)

  • You open the page → it asks Open-Meteo for the next 2 hours of rain at your spot.
  • nowcast.js applies model.json to correct that forecast for Mumbai.
  • It shows the verdict and (if relevant) a flood-spot warning.
  • Meanwhile, in the background, the cron has been logging forecasts vs reality and improving model.json — so next week’s answer is sharper.

One verdict, start to finish — browser → Open-Meteo → apply model.json → answer. (Animated; static frame shown with motion off.)
